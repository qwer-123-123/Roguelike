# 2026-09-07-计划-菌核狂潮 MVP 架构与迭代计划

> 游戏名：菌核狂潮（项目目录名 Roguelike）｜引擎 Unity 2022.3.62t11｜类型 2D 俯视角 Roguelike + 割草

## 目标

把「菌核狂潮」从空工程推进到**2D 最小可玩原型（MVP）**，并建立可持续迭代的 QFramework 四层架构。MVP 交付标准：玩家移动 + 自动攻击 + 怪潮刷怪 + 死亡重开 + 局内升级三选一，形成完整一局可玩的循环。

## 范围

### 包含（MVP 阶段）

- QFramework 四层架构骨架（Controller / System / Model / Utility + Command/Event/BindableProperty）
- 玩家移动 + 自动攻击（自动瞄准最近敌人的远程投射物）
- 敌人（小怪）生成、追击、受击、死亡
- 波次/刷怪与难度随时间递增（基础版）
- 经验掉落拾取 + 升级「三选一」（主动/被动技能）
- 玩家血量、死亡、游戏结束、重开
- 基础 UI（血条、经验条、升级面板、计时/波次）
- 对象池（割草游戏大量同屏敌人/投射物的性能基础）

### 非目标（MVP 明确不做，留后续迭代）

- 局外元进度 / 永久升级
- 精英怪、BOSS、宝箱怪（策划案里的怪物分级，后续迭代）
- 增益道具的完整种类（MVP 只做经验掉落，道具种类后续扩展）
- 正式美术 / 音效（MVP 用占位方块/临时 Sprite）
- 存档、多场景、热更、性能深优化
- 手柄/移动端适配（先 PC 键鼠/键盘）

## 架构设计

### 1. 总体分层（QFramework 四层）

采用 QFramework v1.0.257 的四层架构，`Architecture<T>` 单例作为 IOC 容器统一注册。

```
表现层 IController   ── MonoBehaviour，读输入/驱动 View，发 Command
系统层 ISystem       ── 业务逻辑（战斗/刷怪/升级/关卡），无 Unity 对象依赖，可测试
数据层 IModel        ── 仅「时间共享 / 物理共享 / 配置表」三类数据
工具层 IUtility      ── 对象池等基础设施封装
Command/Query        ── 无状态操作对象（增删改用 Command，查用 Query）
```

### 2. 目录 / 命名空间结构

```
Assets/
├── Scenes/                      # 场景（场景本身独占一个 AB，见 ResKit 规则）
├── Art/                         # 占位美术（后续替换）
├── Configs/                     # ScriptableObject 配置（技能/怪物/波次表）
├── QFramework/                  # QFramework.cs 单文件 + Toolkits（ResKit/ActionKit/PoolKit）
└── Scripts/
    ├── GameArchitecture.cs      # Architecture<GameArchitecture> 单例，统一注册
    ├── System/                  # 业务系统层
    │   ├── ICombatSystem.cs / CombatSystem.cs     # 伤害计算、击杀、经验结算
    │   ├── ISpawnSystem.cs / SpawnSystem.cs       # 刷怪、波次、难度递增
    │   ├── IUpgradeSystem.cs / UpgradeSystem.cs   # 升级三选一、技能生效
    │   └── ILevelSystem.cs / LevelSystem.cs       # 关卡流程：开始/结束/重开
    ├── Model/
    │   └── IGameStateModel.cs / GameStateModel.cs # 游戏阶段、波次、分数、存活时间
    ├── Utility/
    │   └── IPoolUtility.cs / PoolUtility.cs       # 对象池（敌人/投射物）
    ├── Controller/               # 表现层 MonoBehaviour
    │   ├── PlayerController.cs   # 玩家移动 + 自动攻击触发器
    │   ├── EnemyController.cs    # 敌人追击 + 受击/死亡表现
    │   ├── ProjectileController.cs
    │   └── UI/ (HUD、UpgradePanel 等 View)
    ├── Command/                  # 无状态命令
    │   ├── SpawnEnemyCommand.cs
    │   ├── EnemyKilledCommand.cs
    │   ├── ChooseUpgradeCommand.cs
    │   ├── PickupExpCommand.cs
    │   └── StartGameCommand.cs / EndGameCommand.cs
    └── Event/                    # 事件定义（struct，减少 GC）
        ├── OnEnemyKilledEvent.cs
        ├── OnPlayerLevelUpEvent.cs
        └── OnGameOverEvent.cs
```

### 3. 各层职责与数据归属（关键判断）

| 数据/职责 | 归属 | 理由 |
|-----------|------|------|
| 敌人血量、位置、AI 状态 | `EnemyController`（MonoBehaviour） | 运行时实体状态不放 Model（QFramework 明确反例） |
| 玩家血量、位置 | `PlayerController` 或局部数据组件 | 同上 |
| 游戏阶段、波次、分数、存活时间 | `IGameStateModel`（BindableProperty） | 物理共享：跨系统/跨 View 查询 |
| 技能/怪物/波次数值 | `Configs/` ScriptableObject | 配置表，开发期配置，运行时查询 |
| 战斗计算（伤害/击杀/经验） | `ICombatSystem` | 无 Unity 依赖，可单测 |
| 刷怪/波次 | `ISpawnSystem` | 业务逻辑集中 |

### 4. 核心数据流（击杀 → 经验 → 升级）

1. `EnemyController` 检测受击死亡 → `SendCommand<EnemyKilledCommand>`（或发 `OnEnemyKilledEvent`）
2. `CombatSystem` 结算击杀：加经验、生成掉落 → 经验值写回 `GameStateModel`
3. 经验达标 → `UpgradeSystem` 触发升级 → 发 `OnPlayerLevelUpEvent`
4. `UpgradePanelController`（表现层）监听事件 → 弹出三选一
5. 玩家选择 → `SendCommand<ChooseUpgradeCommand>` → `UpgradeSystem` 应用技能 → 通知表现层

### 5. 关键设计原则

- **确定性**：战斗/掉落/升级判定确定性计算，随机只用于「三选一抽技能」「刷怪位置」等非核心结果（符合项目约定）。
- **状态不可原地改**：变更走 Command，状态对象用副本替换或显式方法。
- **下层不依赖上层**：System/Model 不引用 Controller；向上通信用 Event/BindableProperty。
- **性能（割草核心）**：敌人/投射物走对象池；敌人 AI 用「直线追击 + 简单分离」而非 NavMesh；碰撞用距离/OverlapCircle 检测，避免大量刚体碰撞体；同图资源合 SpriteAtlas。

## 推荐推进方向

1. **先骨架后玩法**：迭代 0 把 QFramework 四层和目录、asmdef 立起来，后续每个系统都是「在既有分层里加文件」，避免返工。
2. **移动→敌人→战斗→肉鸽→收口**：每步都是上一个的可玩增量，且每步都能在 Play 模式立刻验证，风险后置最少。
3. **一个迭代一个闭环**：每个迭代完成即写 `Docs/IterationLogs/` 独立日志，并经用户确认后再进下一迭代（M/L 级门禁）。
4. **占位资源先行**：MVP 全程用方块/临时 Sprite，美术最后统一替换（迭代 9），避免早期卡在资源上。
5. **战斗模型默认方案**：自动瞄准最近敌人的**远程投射物**（最贴合割草、易扩展技能弹道）；若想更快，可退化为「周期性近战范围脉冲」，该细节在迭代 3 内确认。

- 每迭代：Unity 编译通过（Console 无 Error）+ Play 模式运行态验证（对应迭代的「验证方式」列）。
