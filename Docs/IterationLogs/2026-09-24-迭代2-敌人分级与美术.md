## 关键步骤

1. **新增 `EnemyDefinition` 配置表类型**（11 种敌人），并把数值从预制体的 `SerializeField` 挪进去 —— 消掉工程遗留项「数值硬编码在预制体上」。加一种敌人从此只需加一个 SO。
2. **抽出 `ISpriteProvider` 接口**：`CharacterSpriteSet`（兵种）与 `EnemyDefinition`（敌人）都实现它，`CharacterView` 只认这一个接口。抽这层的动机是两者的动画数据结构完全相同（帧数组 + 帧时长 + 锚点 + 缩放）但语义不同 —— 若让敌人复用 `CharacterSpriteSet`，它的 `Validate()` 会因 weapon 为空而误报；若各写一套表现组件，帧推进逻辑要复制两份。
3. **`EnemyController` 重写**：改由 `EnemyDefinition` 驱动、加分离力、加血条、补对象池复用的表现复位。
4. **`EnemySpawner` 重写**：从固定半径的圆改成**沿视野矩形贴边生成**（H5 的做法），支持加权随机挑敌人；刷新间隔仍只来自 `IDifficultySystem`（工程「难度单一来源」约定）。
5. **新增编辑器工具**：`EnemyPrefabBuilder`（重建敌人 / 经验掉落物预制体）、`SceneWirer` 扩展（把 11 种敌人装进刷怪池）。
6. **`ConfigBuilder` 扩展**：生成 11 份 `EnemyDefinition`，从 `Manifest.csv` 读锚点。

## 设计决策

- **1 个敌人预制体 + 11 份配置，而不是 11 个预制体。** 后者只是把同一套结构（根 + Visual + 血条）复制 11 遍，彼此只有 `definition` 字段不同。敌人本身仍是**预制体实例**，不是代码搭建的。
- **原地覆盖 `Enemy.prefab`**（`SaveAsPrefabAsset` 保留原 `.meta` 的 GUID），否则场景里 `EnemySpawner.enemyPrefab` 的引用会断。若改成删除后新建，GUID 会变、引用全断。
- **血条用两张 PPU=1 的纯色 sprite**（自制 `white_1x1.png`），靠 `localScale` 表达比例、靠左端对齐的 `localPosition` 表达填充方向。不用 `Image.fillAmount` —— 那是 UI 组件，这是世界空间的 SpriteRenderer；且工程有「无 sprite 的 Image 上 fillAmount 不生效」的记录。
- **血条挂在根节点下、与 `Visual` 平级**，不放进 `Visual`。因为 `Visual` 会被旋转到朝向玩家，血条跟着转就不可读了。
- **BOSS 不放进随机刷怪池**，留待波次触发（迭代 3）—— 随机刷出来会破坏节奏。
- **分离力系数放 `GameConfig`**（默认 3.2）。H5 里同一问题出现过：初版 0.55 太弱，敌人全叠在玩家身上糊成一团，调到 3.2 才散得开。

## 验证结果

- ✅ **编译 0 错误**；运行态 **0 错误**
- ✅ **11 份敌人配置生成**，`EnemyTable` 数值原样来自 H5 `data.js`
- ✅ **`Enemy.prefab` 重建正确**：节点为 `Enemy` + `Visual` + `HpBarBg` + `HpBarFill`，**Cube 网格残留 0 处**
- ✅ **刷怪池接线正确**：`enemyPool` 8 项（BOSS 已排除），`enemyWeights` = `[10,10,10,10,5,5,2,2]`
- ✅ **运行态截图**：敌人全部为真实僵尸精灵、玩家为真实角色、**场上再无白色方块**；血量满时血条隐藏（符合设计），可看到一枚绿色经验球
- ✅ **分离力生效**：同屏数只敌人分散开来，未叠成一坨

**这一轮同时确证了用户对「光圈」的判断**：那些白方块确实是**敌人死后掉落的经验球**（`ExpDrop` 当时还是 Cube）。成因是敌人贴着玩家被击杀、掉落就落在玩家脚下，而自动化验证里玩家不动所以越积越多 —— 实际游玩时会移动并自动吸附拾取，不会堆积。

## 遗留说明

**我在这轮又犯了一次「没验证就下结论」，记录在此。**

我曾断言「迭代 2 的真正瓶颈是 draw call —— 同屏 80 敌 = 80 次 draw call，需要 SpriteAtlas」，并据此把这个包写进了迭代 2 的交付项。

**这是错的**：同类型敌人**共用同一张贴图**，Unity 的 sprite batcher 会自动合批。实际 draw call ≈ 视野内不同贴图的数量（8 种敌人 + 玩家 + 掉落 + 投射物 ≈ **15~20**），桌面端无压力。

已修正计划的风险 R13：**暂不引入 `com.unity.2d.sprite`**。REST 没有测 draw call 的技能，无法实测；且该包本机无缓存、安装需联网，而网络当前不稳。留作真碰到性能问题时的选项。

> **加上迭代 0 的「重采样可降 4~6 倍」，这是同一次会话里我第二次给出未经核实的性能结论。** 两次都是「听起来合理所以没算」。后续涉及性能的判断**必须先给出算式或实测数据**，拿不到就说拿不到。

**其他遗留**：
- 玩家死亡瞬间仍立即进 `GameOver` 阶段；`CharacterView` 已允许死亡动画在 `GameOver` 下播完，视觉上不僵住，但没有「等动画播完再切阶段」的处理
- 波次构成表（哪种敌人、多少只、BOSS 何时出）是迭代 3 的事，本轮先按权重随机
- 中文字体仍未提供，界面与敌人名都是 ASCII 占位
