## 失误记录（重要）

**做了什么：** 用 `filter-branch --index-filter 'git rm -r --cached …'` 摘除素材。`--cached` 只动索引，本以为工作区文件不受影响。

**实际发生：** filter-branch 收尾时会把工作区重置到改写后的新提交，而新提交里已没有那 548 个文件，**于是它们被从磁盘上删掉了**。

**怎么发现的：** 重写后按惯例核对「本地文件是否还在」，`find` 返回 0 个文件。

**怎么修的：** 素材 blob 仍在对象库里（旧提交由 `refs/original` 引用着，尚未 gc），故
`git checkout refs/original/refs/heads/main -- <两个路径>` 完整还原 548 个文件，
再用 `git rm -r --cached` 把它们从索引移出（它们已被 `.gitignore` 覆盖，此后不再被跟踪）。
**还原发生在删除 `refs/original` 与 `gc` 之前** —— 顺序错了就救不回来了。

**教训：** `filter-branch` 类重写历史操作，`--index-filter` 的 `--cached` **不保证工作区安全**，因为收尾的 reset 会按新树对齐工作区。凡涉及「从历史移除但要在本地保留」的需求，**必须先备份工作区（或先确认对象仍可达）再执行**。

## 设计决策

- **排除而非改变可见性**：用户选的是公开仓库。在 R11 未读之前，把第三方素材摘出去比「改成私有」更彻底 —— 私有仓库理论上仍是向托管方分发，且无法排除将来某天改公开时的误操作。
- **用 filter-branch 而非 filter-repo**：本机未装 `git filter-repo`，且只有 4 个提交、无远程（当时），filter-branch 足够且可控。
- **`--prune-empty` 未误伤**：4 个提交摘除素材后仍含其它文件，无提交被剪掉，提交数仍为 4。
- **保留 QFramework**：MIT 授权 + 版权头完整，属合规再分发。若将来要更严谨，可补一个 `THIRD-PARTY-NOTICES`。
- **未替用户选 LICENSE**：公开仓库无 LICENSE 即默认「保留所有权利」。是否开源、用哪个协议是用户的决定，不代选。
